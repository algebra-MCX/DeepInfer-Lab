# 性能分析报告 C1：MoE 只合并本地行，原地反量化

2026-10-22 · 代码 `5f5fb73`（改动前 `32e2b5b`，即 B1）

## 结论

真实 V4.1 四卡 prefill 吞吐从 3,377 提高到 **4,316 tok/s/GPU（+27.8%）**，每步从 1,213 ms 降到 949 ms，和改动前
根据微基准做的预测（约 950 ms）一致。到官方的差距从 10.7 倍缩小到 **8.4 倍**，DeepInfer-Lab 达到官方的 11.9%。MoE 从
701 ms/步降到 410 ms/步，专家部分从 526 ms 降到 252 ms。现在注意力（432 ms）重新成为最大的一项，其中 182 ms 是
拼接 key 的胶水操作。

## 实验设置

与报告 A、B1 相同：真实 V4.1-Flash（`dba1be0`），4 × B200，EP4 / DP4，共享 workload，10 个稳态步。

- 吞吐：`tools/bench_rev.py run perf/fused-index-scores perf/moe-combine --suite real4`，两个版本在同一个作业 9349
  里交替运行。
- profile：作业 9351。profile 作业里同一版本测得 4,320.4 tok/s/GPU，和 9349 相差 0.1%。

## 路由专家内部（ms/步）

| kernel | 改动前 | 改动后 | 说明 |
| --- | ---: | ---: | --- |
| FP4 反量化 | 128.1 | 132.3 | 直接读 E8M0 scale，计算量不变 |
| 反量化结果整块拷贝（Memcpy DtoD） | 85.7 | **0.1** | 反量化直接写进 bf16 权重栈 |
| bf16 转换（`.float()` 等） | 66.0 | **0** | GEMM 输出保持 bf16 |
| `index_copy_` 还原排序 | 59.0 | **0** | 换成 combine kernel |
| `where` 置零非本地行 | 55.8 | **0** | combine 不读非本地行 |
| 按 slot 求和 | 16.5 | **0** | 并入 combine |
| combine kernel | — | **4.0** | |
| grouped GEMM | 67.1 | 66.0 | |
| SwiGLU、gather、排序 | 约 45 | 约 47 | |
| **合计** | **526** | **252** | −52% |

- **为什么旧实现慢：** `GroupedExperts` 的输出按排序后的 [T·k, 5120] 行排列，T·k = 98,304，其中只有约 1/4 来自
  本 rank 的专家。旧代码把整块转成 fp32（2 GB/层），用 `where` 把非本地行置零，再 `index_copy_` 还原顺序、按 slot
  求和，大部分搬运的是零。
- **combine kernel 怎么做：** 对每个 token 按 slot 顺序，只读本地专家的那几行，在 fp32 里累加，一次写出 [T, 5120]。
  求和顺序和原来一样，结果是确定的。非本地行 GEMM 本来就不写，也不会被读到。
- **反量化：** 直接写进栈里对应的切片，省掉了每层 6.8 GB 的 bf16 拷贝。E8M0 scale 在 kernel 里解码，0 和 255 这
  两个边界值单独处理（分别对应 fp32 次正规数 2^-127 和 NaN）。

单层微基准（1 × B200，16,384 个 token，top-6，本 rank 96 个专家）：12.93 → 6.24 ms，输出校验和相同
（5.480333e+04），峰值显存 8.7 → 7.7 GiB。

## 精度

- combine 的求和顺序和旧实现一致，单测要求和旧实现的误差 ≤ 1e-6。
- 反量化与 CPU 参考逐位相等：`test_fp4_all_codes_and_scales` 遍历了全部 256 种字节和 256 种 E8M0 指数，包括有符号
  零、溢出、下溢和 NaN。
- 端到端参考测试全部通过。全量 178 passed。
