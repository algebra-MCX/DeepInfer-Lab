# 性能分析报告 A：稀疏注意力改用 tensor core

2026-10-22 · PR #38 · 代码 `804f4b0`（改动前 `eac0347`）

## 结论

真实 V4.1 四卡 prefill 吞吐从 1,085 提高到 **2,572 tok/s/GPU（2.37 倍）**，每步从 3,776 ms 降到 1,593 ms。
到官方的差距从 33.3 倍缩小到 **14.1 倍**，mini 达到官方的 7.1%。稀疏注意力 kernel 从 2,255 ms/步降到
98.8 ms/步（22.8 倍），不再是瓶颈。现在最大的两项是 MoE（726 ms）和 indexer（461 ms）。

## Kernel 分析

| 形状 (T, H, K, D) | 旧 (ms) | 新 (ms) | 加速 | 新 TFLOP/s |
| --- | ---: | ---: | ---: | ---: |
| 256, 64, 640, 512（真实压缩层） | 3.672 | 0.166 | 22.1× | 129 |
| 256, 64, 128, 512（真实无压缩层） | 0.686 | 0.069 | 9.9× | 62 |
| 256, 4, 640, 512（tiny 模型） | 0.284 | 0.105 | 2.7× | 13 |

- **为什么快：** 一个 query 的 64 个 head 共享同一组 640 个 key。旧 kernel 每个 (query, head) 是一个 program，用
  `tl.sum` 在 CUDA core 上算，同一组 key 被读了 64 × 2 次。新 kernel 把 32 个 head 拼成 `tl.dot` 的 M 维，走
  tensor core，每组 key 每个 head 块只读一遍 QK，再读一遍 PV。
- **离峰值还有多远：** 每步注意力约 13.2 TFLOP，98.8 ms 相当于 134 TFLOP/s，约为 B200 稠密 bf16 峰值的 6%。官方
  14.9 ms 约 0.89 PFLOP/s。
- **剩余差距的原因：**
  1. M 只有 32，tensor core tile 偏小。HEADS=64 时 fp32 累加器 [64, 512] 放不进寄存器，会溢出，扫参也证实了这点。
  2. 两遍算法要多写读一次 scores scratch。
  3. kernel 外面还有约 180 ms 的 gather/拷贝，用来把 key 拼成 [T, 640, 512]。
- **tiny 模型收益小：** 它只有 4 个 head，凑不满 M=16 的 tile，共享 key 带来的收益有限。

## 精度

- 与 fp32 CPU 参考的最大误差和旧 kernel 同一量级（≤ 4.9e-4）。tensor core 的累加顺序不同，所以和旧 kernel 不是
  逐位相等。
- bf16 概率舍入回归 fixture 仍然通过：去掉 bf16 舍入，或把 sink 算进最大值，这个 fixture 都会失败。
- 端到端参考测试全部通过（golden token、参考轨迹逐位置 logits、chunked prefill、抢占）。全量 163 passed。
